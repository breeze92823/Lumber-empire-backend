# Lumber Empire — BACKEND (game server)

Frontend (3D client) lives at `../Lumber-empire`. Colyseus + Mongo, hosted on Bloxity Legion.

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { userId, username, pfp, token, avatar, plot, pose })`). A room is one world of `PLOT_COUNT` (6) yards, so `ROOM_MAX_CLIENTS` is 6: a seventh player gets a new room. Client-authoritative: the server only bounds/sanitises what it stores or relays. `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only.
- The client keeps NO progress in the browser: this server's Mongo doc is the player's only save. A guest's (or a serverless session's) progress lasts the page only.
- Identity (`src/auth.ts`): in production the client's Bloxity token is checked with `POST {BLOXITY_API_URL}/v1/auth/game-token/verify` and the id Bloxity names is the account; no token, a refused one, an outage or a `dev-` id all mean guest. Outside production the sent id is trusted, for local play and the tests. Answers are cached by a hash of the token, outages are not.
- Slots (`src/slots.ts`): the lowest free one on join, roster `slot`. Kept through `allowReconnection` and freed by `forgetSession`, so a dropped connection keeps its yard, and an evicted session or a real leave frees it. The client's `PLOTS` table says where each slot stands.
- Rewarded ads (`src/adReward.ts`, `test/AdReward.test.ts`): `adReward` { rewardToken } is checked with `POST {BLOXITY_API_URL}/v1/ads/reward/verify` and answered privately with `adReward` { ok }. An outage is a no.
- Messages client -> server: `saveProgress` (the whole snapshot, debounced client-side), `identify` (`{ userId, username, pfp, token }` after a sign-in/out mid-session), `pose`, `setAvatar`, `setPlot`, `emote`, `adReward`, `yardFast`, `yardSlow`, `yardHello`. Server -> client (private): `progress` (the saved doc, sanitized), `noProgress` (new account, guest, or no database: the client keeps its fresh state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted.
- Nobody can touch another player's yard: every presence message lands on its sender's own roster entry, and a yard frame is stamped with the sender's slot here, never read from the message. `test/Relay.test.ts` holds that line.
- Saved progress shape (`PlayerDoc`, client `main.js` `save.snapshot()`): `money`, `earned`, `rebirths`, `playtime` (s), `owned[]` (sale ids in the order bought, a save replays them in it; `SALE_PATTERN`, floors as `id@1`), `upgrades { id: level }`, `perks[]` (shop items, they outlive a rebirth), `workers`, `maxWorkers`, `hirePrice`, `crates`, Online Gifts `giftTime` (s) and `giftsClaimed[]` (indexes), `lastSeen`. `earned`, `rebirths` and `playtime` are written with `$max`, so a stale save can't lower a leaderboard score.
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): the Leaderboard in the player's own yard. Top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`rebirths`, `earned`, `playtime`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value }] }, ranks: { stat: n | null } }, sent to each client alone after its load and every `LEADERBOARD_EVERY_MS` (room clock). `connectDb` creates a descending index per stat. The test fake supports just that find/countDocuments shape.
- Bloxity's trophy boards (`src/platformBoards.ts`): saved scores are queued and reported every `PLATFORM_BOARD_EVERY_MS` to `{BLOXITY_API_URL}/v1/leaderboards/hosted/{BLOXITY_GAME_ID}/report` as `legion_<id>`; `playtime` in ms. A no-op without `BLOXITY_REPORT_TOKEN`. `PLATFORM_BOARDS` must match the client's `LEADERBOARDS`. The numbers start as the client's, since the game is client-authoritative.
- Presence (`src/presence.ts`, `test/Presence.test.ts`): what the others draw in the world, relayed through the roster as sent, only bounded. Roster fields `x`/`y`/`z` (feet, in the sender's OWN yard's coordinates: each client knows where that yard stands), `yaw` (wrapped to -PI..PI), `speed`, `swing` (0..1), `carryKind`/`carryCount`, `avatar` (Bloxity look JSON `{ equipped, proportions }`, ids only, at most `AVATAR_MAX_LEN`, never parsed), `plot` (the yard JSON `{ owned, levels, rebirths, perks, signs }`, at most `PLOT_MAX_LEN`, never parsed), `uid` (the checked account id, "" for a guest: Bloxity chat messages name their sender by it), `emote` ("<id>#<n>", the last Bloxity emote started: Boxity only tells the player who picked it). Messages `pose` ~10/s, `setAvatar` { avatar }, `setPlot` { plot }, `emote` { emote }; the join options may carry the first three too.
- Live yard frames (`src/relay.ts`): `yardFast` (~5/s, crew) and `yardSlow` (~1/s, logs, belts, trucks, train) are nested arrays of numbers the server relays unread as `[slot, frame]` to everyone else. Anything else, over its budget (`YARD_*_NUMBERS`) or sooner than its gap (`YARD_*_GAP_MS`) is dropped. The last `yardSlow` per slot is kept, and `yardHello` sends a newcomer the other yards as they last stood. The meaning lives in the client's `yard/sync.js`.
- `src/legion-room-reporter.ts` reports this pod's rooms to the matchmaker (Open Rooms, join by id). A no-op without Bloxity's env vars.
- `src/constants.ts` bounds must cover the client's `src/config.js` (ids match `ID_PATTERN`, money up to `CURRENCY_MAX`). A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (keep it 2-100 for party play; no `seatCap`: the SDK docs say the matchmaker sizes pods, though the hosting docs page still describes `seatCap`). Needs repo var/secret `LEGION_GAME_ID` (= `lumber-empire`) and secret `LEGION_DEPLOY_TOKEN`.
